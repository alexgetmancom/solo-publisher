# Telegram bot — parity specification (TS → Rust)

Contract for reproducing the Studio Telegram bot 1:1. Source of truth: branch `rust` (same TS sources as `main`),
`apps/backend/src/bot.ts`, `apps/backend/src/bot/**`, `apps/backend/src/interfaces/telegram/**`,
`apps/backend/src/botTargets.ts`, catalog `apps/backend/src/foundation/i18n/catalog.ts`.
All paths below are relative to `apps/backend/src/` unless they start with `apps/`, `tests/` or `deploy/`.

Conventions in this document:

- `t(key)` = catalog lookup in the actor's interface locale (`en` | `ru`, default `ru`), `{x}` placeholders. Every
  key is listed verbatim (EN + RU) in **Appendix A**. When a screen is quoted as rendered, it is the EN rendering.
- `[Label → data]` = one inline button; one line in a keyboard block = one keyboard row.
- `md` = `parse_mode: "Markdown"` (legacy Markdown, never MarkdownV2, never HTML). `plain` = no parse_mode.
- `esc(x)` = `escapeMarkdown` (`foundation/markdown.ts:13`): prefixes `\` before each of `\ _ * [ ] \``.
- `trunc(x,n)` = `truncateUnicode` (cut to n code points). Labels "≤N" mean that cut.
- **screen** effect = edit the tapped message in place if this update has not yet written below it, else send new;
  **message** effect = always a new message (see §1.7 Screen anchor).
- "card binding" = row in `interface_bindings` (interfaceId `telegram`) tying a publication to the chat message that
  currently is its live card (§5.5).

Canonical keyboard snapshot generated by the TS test-suite: `apps/backend/tests/screens/bot-screens.txt`
(produced by `tests/botScreens.test.ts`). The Rust port should generate the same snapshot and diff it.

### 1.2 Bot API transformer stack (outgoing calls)

Installed in this order (`bot.ts:37-44`); grammY makes the last-installed the outermost:

1. `installApiTiming` (`bot/api-timing.ts:12`) — measures every call (method + ms) into the per-update tap
   measurement. Not user-visible.
2. `autoRetry({ maxRetryAttempts: 3, maxDelaySeconds: 30, rethrowInternalServerErrors: true })` — retries 429
   (`retry_after`) up to 3 times if the wait ≤ 30 s; 5xx is **not** retried (would risk double send).
3. `installUnchangedEditGuard` (`bot/unchanged-edits.ts:35-61`) — outermost:
   - For `editMessageText` with `chat_id`+`message_id`: key `"<chat>:<msg>"`, content = `JSON.stringify(payload
     minus chat_id/message_id)`. If remembered content equals → **no API call**, returns `{ok:true,result:true}`
     and counts an "unchanged edit". Otherwise sends, and on `ok` remembers.
   - Any other method addressed at a remembered message (`editMessageReplyMarkup`, `deleteMessage`, caption edits…)
     forgets the key first.
   - `sendMessage` success remembers `"<result.chat.id>:<result.message_id>"` with the send payload content (so the
     first identical edit of a freshly sent screen is free).
   - LRU of **200** messages, process-local (empty after restart).
   - The menu plugin's own transformer is per-update and runs *inside* this one, so `reply_markup` is already a
     rendered keyboard when compared.

### 1.4 Authorization

Only Telegram users whose id is in `CONTROLLER_ADMIN_IDS` (positive id list) are actors. The actor id is the
Telegram user id. Per-actor state: interface locale (`settingsService.locale(actorId)`, default `ru`), time zone,
notification settings, conversation sessions. Studio data is shared across accessible actors
(`accessibleStudioActorIds`). Broadcasts (reminders, completions, failures, backups) iterate all admin ids, each in
its own locale and time zone; one failing recipient does not stop the others (`forEachAdmin`,
`interfaces/telegram/video-notifications.ts:266-276`). Alerts go only to `CONTROLLER_ADMIN_IDS[0]`.

### 1.5 Message routing (`bot.ts:147-155`)

For every message not caught by command/hears:

1. `handleSettingsMessage` (`bot/settings/index.ts:19-37`): if a `settings` session is open → handled (§6.6).
   A navigation message (starts with `/`, or equals `☰ Menu`/`☰ Меню`) clears the settings session and falls
   through.
2. `handleIntakeMessage` (`bot/intake.ts:90-127`): only when an `intake` session at step `awaiting` exists (§6.1).
   Its effects are executed; if `handled` stop.
3. `handlePublicationMessage` (`bot/callback-router.ts:144-154`): active session = `video` if present, else `post`;
   dispatch to `handleVideoConversationMessage` (§6.4) or `handlePostMessage` (§6.2). If the video handler declines
   (no session), the post handler answers. A message is never left unanswered: without any open flow the post
   handler replies `t("post.need-new-post")` with the persistent reply keyboard.

### 1.6 Callback routing (`bot.ts:157-174`)

After the menu plugin (which consumes its own format):

1. `parseSessionCallback(data)` strips an optional `sv<revision>|` prefix; if the payload matches
   `^p:(post|video):([^:]+)(?::(.*))?$` → publication router (`handlePublicationCallback`, §5.2).
2. Else `parseScreenCallback(data)` → `SCREEN_ROUTES[id]` (§5.3). Handler returns `true` when it acted.
3. Not parsed, or handler returned `false` → `answerCallbackQuery({text: t("action.unknown")})` → delivered as a new
   chat message `"Unknown action"` (because of the redirect in §1.3 #3).

### 1.7 Screen anchor — edit-in-place vs new message (`bot/effects.ts:106-148`)

Every screen render inside one update goes through one `ScreenAnchor` per effect batch:

- Anchor = `callback_query.message.message_id` if the update is a callback, else none.
- `render(overAnchor=true)` ("screen"): if an anchor is still unspent → `editMessageText(text, options)` on the
  tapped message; success or `"message is not modified"` → anchor spent, returns that message id. Any other edit
  error (e.g. message has media) → log `warn "screen could not be edited in place"` and fall back to `reply`.
- `render(false)` ("message") or no anchor → `ctx.reply(text, options)` (new message in the same chat), anchor spent.
- `photo` and `delivery-previews` effects spend the anchor (everything after them is sent below).
- Consequence: within one update only the **first** screen edits; subsequent screens are new messages below.
- `showScreen(ctx,text,opts)` = a fresh anchor + screen; `showMessage` = a fresh anchor + message. Each call makes its
  own anchor, so two consecutive `showScreen` calls in one handler both try to edit the tapped message (see
  settings language switch §4.10.6, intake download §6.1.6).
- Toast-type effects (`answerCallbackQuery` with text) use their own `showMessage` (redirect, §1.3) and do **not**
  spend the effect batch's anchor: `[toast, screen]` ⇒ toast text arrives as a new message at the bottom and the
  screen then edits the tapped message above it.

### 1.8 Effect executor (`bot/effects.ts:19-90`)

Handlers return ordered `PublicationEffect[]`, executed strictly in order:

| Effect | Execution |
|---|---|
| `answer-callback {text?, showAlert?}` | `ctx.answerCallbackQuery(...)` — with text → new chat message (redirect); without → no-op |
| `toast {text, showAlert?}` | same as above with text (always a message) |
| `screen {text, options, card?}` | anchor.render(true); if `card` given and a message id resulted → bind card (§5.5) |
| `message {text, options, card?}` | anchor.render(false); bind card |
| `edit-reply-markup {keyboard}` | `editMessageReplyMarkup` on the tapped message (declared, no current emitter) |
| `photo {path, options, card?}` | spend anchor; `replyWithPhoto(InputFile(path), options)`; bind card |
| `delivery-previews {projections, locale}` | spend anchor; send delivery previews (§7.6) |
| `main-menu {menu, text}` | anchor.render(true, text, {reply_markup: mainMenu}) |
| `session clear {kind, actorId}` | retire conversation session of that kind |
| `session save {actorId, state}` | save conversation session |

`runCallbackAction` (`bot/callback-effects.ts:27-43`) wraps every publication/intake tap: acquires the process-local
action lock `lockKey` (TTL 5 min, `foundation/action-lock.ts:16-25`); if already held → effects =
`[toast t("action.in-flight")]` = `"Already running…"`. If the produced effects contain no `answer-callback`/`toast`,
an empty `answer-callback` is prepended. A thrown error → `onError` (log) and `[toast callbackToast(describe(error))]`.

### 1.9 Error texts

- `describeError(locale, err)` (`foundation/i18n/index.ts:10-13`): a `StudioError` whose code is a catalog key →
  `t(code, params)`; anything else → raw `error.message` / `String(error)` (English internals may reach the admin).
- `describePublicationError` (`bot/error-text.ts:12-16`): `common.schedule-parse-error` gets `{timezone}` =
  actor's `TIMEZONE_LABEL`.
- `isUnchangedMessageEdit(err)` ⇔ `String(err)` contains `"message is not modified"` (`bot/telegram-errors.ts:9-11`).

### 1.10 Rate limiting and API timing

- No outbound throttler. 429 handled by auto-retry (§1.2).
- Inbound: per-chat serialization; callback dedupe (15 min / 10 000); supersession dropping of redundant taps
  (§5.4); action locks (5 min TTL) keyed per workflow; unchanged-edit suppression (200-entry LRU).
- Deploy actions are fire-and-forget (not awaited) because they can take ~150 s (§4.12).
- Story-card wait: polls every 1 s, up to 60 s (§6.3.4). Album settle: 4 s (§6.5). Video download retries: 2 s, 5 s.

## 4. Screens

Each screen: id/route · source · text · keyboard · conditions · actions · render mode.

### 4.1 Main menu — `main-menu` (menu plugin)

- Source: built `bot/navigation.ts:15-55`, text `bot/menu-render.ts:33-81`, shown by `showMainMenu`
  (`bot/menu-render.ts:27-31`) as effect `main-menu` (screen: edits the tapped message on a callback; new message
  on `/start`, `☰ Menu`).
- Menu fingerprint: `publishing:<locale>` (replaces the plugin's label hash, so a changing queue count never makes
  the menu "outdated"; a locale change does).
- Text (plain, no parse_mode) = headline:
  - item = first upcoming queue item, else latest published item (`queueService.headline`,
    `studio/services/queue.ts:46-63`); none → `t("menu.queue-empty")` = `"✅ Queue is empty"`.
  - Otherwise `"<prefix> <time> · <label>"` where prefix = `⏰` (upcoming and overdue), `⏭` (upcoming), `✅`
    (published).
  - time: same zoned calendar day as now → `HH:MM` (24 h, `formatZonedClock`, locale tag `en-GB`/`ru-RU`); else
    `formatQueueTime` (`bot/queue-time.ts:11-18`): day distance −1 → `"<Yesterday>, HH:MM"`, +1 →
    `"<Tomorrow>, HH:MM"`, else `"<D Mon>, HH:MM"` (`Intl` `{day:"numeric", month:"short"}`, e.g. `5 Aug` /
    `5 авг.`). (distance 0 cannot occur here.)
  - label: strip one leading Extended_Pictographic emoji (+ optional `U+FE0F`/skin modifier) and following spaces,
    trim (fallback: original); if > 20 code points → cut to 20; if the cut ends at a word boundary (cut had trailing
    whitespace, or char #21 is a space) keep it trimmed, else cut back to the last space (unless no space at
    index > 0); append `"..."` (three ASCII dots).
  - Published label = first line of the post text (post) or video label, whitespace collapsed, trunc 38, trim.
- Keyboard (`bot-screens.txt` "Main menu"):
  ```
  [📝 Text] [🎬 Video]
  [📋 Work queue · {count}] [⚙️ Settings]
  ```
  - `menu.work-queue-count` when `pending = upcoming + drafts` > 0, else `menu.work-queue` (`📋 Work queue`).
  - `📝 Text` → `openIntake(text)`; `🎬 Video` → `openIntake(video)` (§6.1, screen over the menu message).
  - `📋 Work queue` → `showQueue(page 0)` (§4.3).
  - `⚙️ Settings` (`t("settings.title")`) → submenu `settings-menu`; handler `showScreen(t("settings.title"))`
    (plain) with the settings keyboard.

### 4.2 Intake prompt — `intake_cancel`

- Source `bot/intake.ts:75-87`. Screen (edits tapped message, or new on hears).
- Text (plain): text entry `t("intake.prompt-text")` = `"📝 Send the text, photos or an .md file."`; video entry
  `t("intake.prompt-video")` = `"🎬 Send the video file."`.
- Keyboard: `[← Cancel → intake_cancel]` (`common.cancel`).
- Side effect: aborts any running video download for the actor; saves session `intake/awaiting {entry}`.
- `intake_cancel` → cancel intake (abort download, clear session) → effect `main-menu` (screen) (§4.1).

### 4.3 Work queue — `queue_home`, `queue_page:<page>`

- Source `bot/queue.ts:23-112,118-172`. Screen, `md`.
- Text: `📋 *{t("queue.title")}*` = `📋 *Work queue*` (always just the title).
- Data (`studio/services/queue.ts:64-145`, ≤100 rows per kind):
  - upcoming = scheduled posts without a schedule gap (time = earliest of RU/EN times) + scheduled videos (time =
    earliest scheduled target), sorted ascending; `overdue` when time ≤ now.
  - drafts = posts with a schedule gap (label prefixed `⏳ `), posts `needs_review`, videos `draft`/`editing`;
    sorted by `updatedAt` descending.
  - attention = items in `actionableIssues` (sorted updatedAt desc).
  - label: post = first line of `text_ru` (or `Post #<id>`), video = label (or `Video #<id>`); whitespace
    collapsed, trunc 38, trimmed.
- Paging: page size 10 items (upcoming+drafts mixed). Upcoming grouped by zoned calendar day; a whole day group
  (≤10 items) is not split across pages when the page already has upcoming items and would overflow; then drafts.
  Requested page clamped to `[0, pages-1]`. Empty → one empty page.
- Keyboard (each row closed):
  ```
  [<upcoming item>]                 one row each → p:<kind>:view:<id>:overview
  [<kind icon> <label>]             one row per draft → p:<kind>:view:<id>:overview
  [⚠️ Needs attention ({count})]    → queue_attention      (only if attention non-empty; count = all attention)
  [←] [<p>/<pages>] [→]             only if pages > 1; ← only if page>0 → queue_page:<p-1>; label → noop; → only if not last → queue_page:<p+1>
  [← Menu → menu_home]
  ```
  - upcoming button text = trunc 60 of `"<⏰ if overdue>{formatQueueTime} · <icon> <label>< · N platforms>"` —

## 5. Callback data

Telegram limit: 64 bytes of `callback_data`. Three disjoint namespaces.

### 5.1 Grammar

```
callback      := menu-cb | session-cb | screen-cb
menu-cb       := <menuId> "/" <row> "/" <col> "/" <payload> "/" <hash>      ; @grammyjs/menu internal (§5.7)
session-cb    := [ "sv" <revision:digits> "|" ] publication-cb
publication-cb:= "p:" ("post"|"video") ":" <action:[^:]+> [ ":" <arg> ( ":" <arg> )* ]
screen-cb     := <screenId> ( ":" <arg> )*                                   ; exact arity per id
arg           := 1*(any char except ":")      ; builder throws action.invalid-callback-argument on ":" (and on "" for screen args)
```

- Builders: `publicationCallback(kind, action, args, revision?)` (`bot/publication-callback.ts:22-35`),
  `versionedCallback` (`:57-59`), `screenCallback(id, args)` (`bot/screen-callback.ts:56-65`, arity checked).
- Parsers: `parseSessionCallback` (`:62-71`) with `^sv(\d+)\|(.*)$`; `parsePublicationCallback` (`:38-47`);
  `parseScreenCallback` (`bot/screen-callback.ts:69-76`) — unknown id or wrong arity → null.
- Draft id args: `parseDraftId` — positive safe integer, else invalid. Screen numeric args: `screenNumber(v,
  {min})` — safe integer ≥ min (pages min 0, draft/id min 1).
- Versioning: `sv<n>|` carries the conversation-session revision for dialog buttons. Required when the action
  declares `sessionRevision` (missing → stale). When present it must equal the current session revision of that
  kind, else `StudioError("action.session-stale")` → message `This dialog is outdated. Start again.`.

### 5.2 Publication router (`bot/callback-router.ts:53-135`)

Order of checks for a `p:` callback (inside `runCallbackAction`, lock key `"<actorId>:<payload without sv>"`):

1. Unknown action for kind → `[answer "This card is outdated. Open the current card from the queue.", message same
   text with keyboard [📋 Work queue → queue_home]]`.
2. `entity:"draft"` and first arg not a positive id → toast `Invalid post` (post) / `t("err.video-reopen-create")`
   (video).
3. Arg count ≠ declared (excluding draft id) → toast card-stale (no message).
4. `sessionRevision` declared and no `sv` prefix → toast card-stale.
5. `sv` present → `requireSessionRevision(session(kind).revision, rev)` → error toast session-stale.
6. Draft id → `pipeline.get(actorId, id)` (throws when the actor cannot open it → error toast).
7. `freshCard` declared and the tapped message is not the current card of that publication (a binding exists and its
   message id differs) → `[toast card-stale, message <current card re-rendered (default view)>]` (card re-bound to
   the new message at the bottom).
8. Run handler.
Errors anywhere → log `error "Publication action failed"` and toast = `callbackToast(describePublicationError)`.

### 5.4 Supersession (stale-tap dropping) — `bot/callback-boundary.ts:187-219`

Only for screen callbacks whose id is supersedable. Key = `"<chatId>:<messageId>:<screenId>"`; each tap takes a
global sequence number at acknowledgement time (arrival order). When a tap reaches the boundary and a later tap has
claimed the same key, the older one is dropped (no handler, no output). The claim is released after the handler.
Args are not part of the key (e.g. `queue_page:1` and `queue_page:2` on the same message supersede each other).

### 5.5 Card freshness and bindings

- Bindings (`interfaces/telegram/control-cards.ts`): table `interface_bindings` (interfaceId `telegram`,
  entityType, entityId) → `conversationId` (chat), `messageId`, `stateJson`. Types: `draft` (post card, state
  `{view}`), `post_progress` (state `{details}`), `video_draft`. Upsert on every bound render.
- `freshCard` actions compare the tapped message id with the bound one (`bot/card-freshness.ts:16-21`); unbound →
  considered fresh.
- Background repaints (`refreshPostPreviewCard`, `refreshPostControlCard`, `refreshVideoControlCard`) edit the bound
  message by chat/message id (post preview repaint keeps the stored view).

### 5.6 Callback boundary rules (summary)

1. Exactly one real `answerCallbackQuery` per tap, sent first, empty (§1.3). All later toasts/alerts → chat
   messages (≤200 code points via `callbackToast` where wrapped; raw elsewhere).
2. Duplicate callback ids (Telegram redelivery) within 15 min → answered, not processed.
3. Same supersedable button on same message tapped again → older dropped.
4. Per-chat serialization after acknowledgement.
5. Action locks (5 min TTL) → `Already running…` message.
6. Errors → message with the localized error text; never an unanswered spinner.
7. Unknown/malformed → `Unknown action` message.

### 5.7 Menu plugin callbacks

`@grammyjs/menu` encodes its buttons as `<menuId>/<row>/<col>/<payload>/<hash>` (see comment
`bot/callback-boundary.ts:127-141`). The hash is the plugin's fingerprint hash: for `main-menu` derived from
`publishing:<locale>`; for settings menus derived from the rendered labels (no fingerprint). On mismatch the plugin
treats the menu as outdated: it re-renders the current keyboard and answers `"Menu was outdated, try again!"` (plugin
default; with the acknowledgement redirect this surfaces as a chat message). URL buttons carry no callback.
**Rust decision required**: either reimplement this exact wire format (so keyboards already in users' chats keep
working after the cutover) or define a new namespace and accept that pre-cutover settings/main-menu keyboards answer
"Unknown action".

## 6. Conversation / input flows

### 6.0 Session store (`bot/conversation-state.ts`)

- One durable row per (actor, kind), kinds `intake`, `post`, `video`, `settings` (`conversationSessions` port).
  Fields: draftId, step, data (JSON), controlMessageId (always null today), active, revision, updatedAt, expiresAt.
- **One active conversation per actor**: saving a kind retires all other kinds first.
- TTL 30 min, refreshed on each save (`expiresAt = now+30min`); a row without expiresAt expires 30 min after
  updatedAt. Expired, inactive, or empty-step rows read as "no session" (expired/empty rows are retired on read).
  No message is sent on expiry; the next tap simply finds the session missing/stale.
- Revision: incremented on save when something semantic changed (active/draftId/step/data); unchanged re-save keeps
  it. `expectedRevision` on save enforces optimistic concurrency. Buttons of dialogs carry it as `sv<rev>|`.
- Active publication session for message routing: `video` wins over `post` (`getActiveConversationState`).

### 6.1 Intake (`bot/intake.ts`) — entry for all new material

1. **Open** (`openIntake`, :75-87): abort the actor's running video download; save `intake/awaiting {entry}`
   (`entry` = `text`|`video`); screen prompt (§4.2).
2. **First message** (`handleIntakeMessage`, :90-127), only at step `awaiting`:
   - `media_group_id` present → clear intake, decline (album goes to the post handler → album collector, §6.5).
   - Extract (`bot/message.ts:4-57`): text = `text` or `caption`; entities = `entities` or `caption_entities`; media:
     largest `photo` size; `video`; `animation` (as video; its twin `document` ignored); `document` only if mime
     `video/*` or name matches `\.(mp4|m4v|mov|webm|mkv|gif)$`i (as video). Each media item keeps file_id, sizes,
     duration, file_name, mime_type, file_size as available.
   - Markdown document (mime starts `text/markdown` or name ends `.md`/`.markdown`/`.mdx`): download via `getFile` +
     `GET {apiBase}/file/bot{token}/{file_path}` with 10 s timeout; > 1 000 000 bytes (declared size, content-length,
     or text length) → `StudioError("intake.file-too-large")` (propagates: message handler throws → no reply,
     logged by bot.catch — **ambiguity**, see §11). Its text replaces the message text.
   - Nothing usable (no markdown, blank text, no media) → screen `t("intake.unsupported")`, intake stays open.
   - Offered kinds: material with a captured video file → `[video, post]`, else `[post, article]`; filtered by entry
     (`text` accepts post+article, `video` accepts video). Empty → screen `t(entry.rejected)` (`intake.need-video`
     for the video entry; `intake.need-text` is unreachable because the text entry always accepts `post`), intake
     stays open.
   - Save `intake/choose` with captured `{message, markdown, video, entry}`.
   - Decide: exactly one offered → it; markdown → `article`; text length (UTF-16 code units) ≤ **900** → `post`;
     else ask: screen `📥 {characters} characters, {media} media. What is this?` (plain; characters = UTF-16 length)
     with one row of offered kind buttons `[📝 Post → intake_kind:post]` `[📄 Article → intake_kind:article]`
     `[🎬 Video publication → intake_kind:video]` and a row `[← Cancel → intake_cancel]`.
3. **post** (`applyIntakeKind`): import media to Content assets (`getFile` + download; photos `.jpg` `image/jpeg`,
   videos `.mp4` `video/mp4`); clear intake; `createPostFromMessage` (`bot/post-screen.ts:82-111`): create draft
   (EN translation is queued, not awaited), clear post session; if largest media `file_size` > 50 000 000 →
   screen `⚠️ This file is {round(MB)} MB. We recommend up to 50 MB: …` (plain) first; then the post card overview
   (md, bound).
4. **article**: save `intake/article_review`; screen (plain) `📄 {title}\n\n{characters} characters in the body.
   Publish as an X Article?`; title = first `# ` heading (or first non-empty line, `Untitled`), characters = parsed
   body text length. Keyboard: `[🐦 Publish to X Article → intake_kind:article_confirm]` / `[📝 Actually, this is a
   post → intake_kind:post]` (only when the kind was decided automatically, i.e. not from a button) /
   `[← Cancel → intake_cancel]`. `article_confirm` → `publishArticle` to every target carrying `article` in the
   first carrier's locale (today `x_article`, EN); none → `intake.no-article-target`; clear intake; screen `📄 {title}
   is queued for X Article.` + result nav.
5. **video destination**: requires captured video (else `intake.expired`); save `intake/video_locale` with
   `targets` = connected video targets (`youtube_shorts`, `instagram_reels` order, from `videoDestinations`).
   Screen (plain) `Which audience is this video for?`; keyboard: if >1 connected, one row of
   `[{✅|⬜} {Label} → intake_target:<target>]`; row `[🇷🇺 RU video → intake_locale:ru] [🇬🇧 EN video →
   intake_locale:en]`; row `[← Cancel → intake_cancel]`. Toggle: removing the last selected → message
   `At least one platform has to stay selected.`; else save and re-render (screen).
6. **video download** (`applyIntakeVideoLocale`, :257-327): requires step `video_locale`, a video, ≥1 selected
   (`err.no-video-platforms-connected`). If a download for the same session revision is running → nothing. Else
   abort the previous one and show screen `⏳ Downloading video from Telegram…` with one row `[↻ Retry download →
   intake_download:<rev>:<ru|en>] [← Cancel → intake_download:<rev>:cancel]`. Then in background (not awaited):
   `storeTelegramVideo` with up to 3 attempts (retry after 2 s, then 5 s) only for `getFile` 400 "wrong file_id or
   the file is temporarily unavailable" or HTTP errors; aborted if the intake session changed. Then technical
   probe; clear intake (only if still current) and save `video/asset` session `{videoLocale}` with selected
   platforms; run `attachVideoAsset` (§6.4.1). Output: if the first effect is not a screen, prepend screen `✅ Video
   downloaded.` (empty inline keyboard). Errors: before hand-off → screen `Could not finish downloading the
   video.\n\n{error}` with the same retry/cancel row; after hand-off → screen `{error}` with empty keyboard. These
   screens edit the tapped (downloading) message.
7. `intake_cancel` / `intake_download:…:cancel` → abort download, clear intake, main menu (screen).
8. Material is read from the session; missing → `intake.expired` (`This material is no longer in the intake. Send

### 6.5 Album collector (`bot/albums.ts`)

- Then send a **new** message: thread step → the thread-part screen (`thread_part` plain question, not bound;
  `thread_edit` thread view md, bound); else post card overview (md, bound).

## 11. Ambiguities and porting notes (decide before/while porting)

1. **Toasts are chat messages.** Because every tap is answered empty on arrival (§1.3), all later
   `answerCallbackQuery({text, show_alert})` calls — validation alerts, "Scheduled", "Queued", settings toasts,
   "Unknown action", cancel-remaining report — are delivered as plain new messages; `show_alert` is never visible.
   This is current behaviour (by design per comments) and must be reproduced, not "fixed".
2. **Menu plugin wire format** (§5.7): `<menuId>/<row>/<col>/<payload>/<hash>` + "Menu was outdated, try again!"
   (plugin default text, surfaces as a chat message). Exact hash algorithm is internal to `@grammyjs/menu` 1.3 (not
   vendored in the repo; `node_modules` absent). Decide: reimplement byte-compatible, or new format + accept stale
   pre-cutover settings/main-menu keyboards.
3. **`post.need-new-post`** tells the user to choose "📥 New material" — a button that no longer exists. Reproduce
   verbatim unless copy is changed deliberately on both sides.
4. **Text entry never rejects**: a video sent via `📝 Text` becomes a *post* carrying the video (offered kinds
   `[video, post]` ∩ `[post, article]` = `[post]`), so `intake.need-text` is unreachable although the code comment
   says the intake "stays open". Tests (`tests/intake.test.ts`) are the arbiter.
5. **Errors thrown in message handlers are silent**: e.g. `intake.file-too-large` from the Markdown download, a
   failing `importTelegramMedia` while creating a post from a decided intake, or `storeTelegramVideo` outside a
   try — they reach `bot.catch` (log only); the user gets no reply.
6. `requireConversationState` throws a plain `Error("action.session-stale")` (not `StudioError`), so the post value
   error would show the raw key text `action.session-stale` inside `I couldn't use that value: …`.
7. `bot.ts:101-102` comment mentions a discussion-group handler before the gate — none exists.
8. `hears("⚙️")` opens Settings but no keyboard offers a bare `⚙️` button any more (manual typing only).
9. `showSettings(..., edit)` has identical branches; `edit-reply-markup` effect has no emitter.
10. Video card `confirm_now` reached via a plain `p:video:view:<id>:confirm_now` (no revision) renders unversioned
    buttons whose `publish_confirm` then fails as stale; only the `publish` action produces a working one.
11. Video time-picker slot callbacks always carry the *first selected target* as `axis`, even in common mode;
    handlers ignore it.
12. Deploy controls: target names `alex`, `maru`, `worker` are hard-coded in the bot; deploy-agent messages and
    their two buttons are hard-coded Russian/English outside the catalog and outside the bot process.
13. **Process-local state** that the Rust port must keep process-local (lost on restart, by design): callback dedupe,
    supersession claims, action locks, unchanged-edit memory, Story-card waiters, video downloads/abort controllers,
    discovered Zernio accounts and "open channel" per actor in settings. Durable: conversation sessions, card
    bindings, pending albums, event delivery claims, daily backup claim.
14. **Text metrics**: `truncateUnicode` counts code points and replaces lone surrogates with `U+FFFD`; intake
    `characters` and the 900-char auto-post rule use JS `string.length` (UTF-16 code units); preview caption limit
    1000 is UTF-16 length; entity offsets are UTF-16 (Telegram native).
15. **Intl formatting parity**: `formatZonedDateTime` (`ru-RU`, `DD.MM.YYYY, HH:MM`), `formatZonedDayMonth`
    (`5 Aug` / `5 авг.`), video confirmation `toLocaleString` (`en-GB` → `20/08/2026, 12:00:00`; `ru-RU` →
    `20.08.2026, 12:00:00`), CLDR plural rules — Rust needs ICU4X or equivalent hand tables; verify against TS
    output for both locales.
16. 56 catalog keys are unreferenced (Appendix A `unref`): keep or drop is a product decision; no screen uses them.
17. Settings input vs navigation: `/start`, `☰ Menu`, `⚙️`, `📝 Text`, `🎬 Video` are consumed by command/`hears`
    handlers *before* `on("message")`, so they do **not** clear an open settings input session (it stays open, ≤30 min,
    and the next plain message is consumed as the time zone / signature). Only other `/…` commands reach
    `isNavigationMessage` and cancel it. Opening the intake does retire it (one active session per actor). Verify
    whether to preserve this exactly.
